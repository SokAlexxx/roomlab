## Історії користувачів і критерії приймання

1. **Пошук вільної кімнати.** Як користувач (alice), я хочу бачити кімнати, вільні в інтервалі, щоб обрати місце.
   - `GET /api/rooms/available/?start&end` без автентифікації → 401.
   - Повертає масив `{id,name,capacity}`, упорядкований за `id`; кімнати з активним/очікуваним бронюванням, що перетинається з `[start,end)`, виключені; суміжні інтервали дозволені.
   - Наївний час або `start>=end` → 400 `invalid_input`.
2. **Бронювання.** Як користувач, я хочу забронювати кімнату, щоб гарантувати слот.
   - `POST /api/bookings/` → 201 зі статусом `ACTIVE` (v1); повтор на той самий слот → 409 `slot_conflict`.
   - Два одночасні запити на той самий слот у реальному PostgreSQL → рівно один 201 і один 409.
3. **Мої бронювання та скасування.** Як власник, я хочу бачити й скасовувати свої бронювання.
   - `GET /api/bookings/mine/` повертає лише власні записи, включно з неактивними.
   - Скасування чужого → 403 `forbidden`, запис не змінюється; відсутнього → 404; неактивного → 409 `invalid_transition`; слот звільняється одразу.
4. **Демо-середовище.** Як учасник демо, я хочу одною командою отримати робочі облікові записи.
   - `python manage.py seed_demo` створює R100 (100), R101 (101), alice, bob, admin; лише admin має `is_staff`.
   - Повторний запуск ідемпотентний: ті самі ID, наявні бронювання не змінюються, паролі скидаються на `DEMO_PASS`; без `DEMO_PASS` команда завершується помилкою, нічого не змінивши.

## Модель станів v1

```
            POST /api/bookings/
   (нема) ─────────────────────▶ ACTIVE ──── cancel (власник) ───▶ CANCELLED
```

- У v1 створюється лише `ACTIVE`; `CANCELLED` — кінцевий стан.
- `PENDING` і `REJECTED` уже є в міграції 0001 та в check-обмеженні `booking_status_valid`, але у v1 не створюються (резерв для v2: `PENDING → ACTIVE | REJECTED`, `PENDING → CANCELLED` власником).
- Будь-який перехід із неактивного стану → 409 `invalid_transition`. Слот займають лише `ACTIVE` (у v2 також `PENDING`).

## Політика асинхронного рев'ю

- Кожна зміна — окрема гілка й PR, прив'язаний до задачі Jira (KAN-…); прямих комітів у `main` немає.
- Зелений CI (Ruff, `makemigrations --check`, міграції, повний набір тестів на PostgreSQL) — обов'язкова умова до рев'ю.
- Рецензент відповідає протягом одного робочого дня; синхронна зустріч не потрібна. Коментарі: «блокує» (порушення контракту, прав, цілісності даних) або «пропозиція».
- Автор не зливає власний PR без схвалення; після змін після схвалення потрібне повторне схвалення.
- Спільні тести `qa/` не змінюються; зміна контракту — лише окремим PR до `docs/contract.md` з погодженням обох.

## ADR-2: права перевіряються лише на сервері

- **Статус:** прийнято.
- **Контекст:** API викликають довільні клієнти; будь-які поля в тілі запиту (owner, status, is_staff) підконтрольні клієнту.
- **Рішення:** особа визначається лише сервером через `booking.http.endpoint` (Basic-автентифікація → `request.user`). Власник бронювання завжди `request.user`; поля `owner`/`status` з тіла ігноруються. Перевірка власника (скасування) і `is_staff` (погодження) виконуються у view перед будь-якою зміною, всередині транзакції з блокуванням рядка. Відмова → 401/403 без мутацій.
- **Наслідки:** клієнт не може підвищити собі права; UI-приховування кнопок не вважається захистом. Кожен ендпоінт, що змінює дані, має тест «чужий/неавторизований → 401/403 і рядок незмінний».

## Вимірювані цілі якості

| Ціль | Метрика й поріг | Метод перевірки |
|------|-----------------|-----------------|
| Доступ | **0** несанкціонованих мутацій: кожна спроба без автентифікації (401), від чужого власника чи не-staff (403) не змінює жодного рядка `Booking`. | Тести порівнюють знімок рядка до/після відмови (напр. `test_owner`: bob → 403, статус лишається `ACTIVE`). |

| Пошук | p95 латентності `GET /api/rooms/available/` **≤ 1 с** на **100 запитів** при **1000 рядків** бронювань. | Скрипт засіює 1000 бронювань, робить 100 автентифікованих запитів (кеш Basic виключає вартість PBKDF2), рахує 95-й перцентиль. |
