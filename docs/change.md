# Зміна v1 → v2: погодження бронювань великих кімнат (KAN-14 / B4)

## 1. Що змінюється
- `POST /api/bookings/`: кімната з `capacity > 100` → запис зі статусом `PENDING` (201); `capacity <= 100` → `ACTIVE`, як у v1.
- `PENDING` займає слот так само, як `ACTIVE` (пошук і конфлікт 409).
- Нові ендпоінти лише для staff: `GET /api/approvals/` (список `PENDING`), `POST /api/approvals/{id}/decision/` `{"decision":"approve"|"reject"}` → 200 `ACTIVE`/`REJECTED` з `decided_by`, `decided_at`, `decision`. Повтор того самого рішення → 200 з початковим аудитом; протилежне → 409 `invalid_transition`.
- Власник може скасувати `PENDING` (вже реалізовано в `flow.CANCELLABLE`).

## 2. Що НЕ змінюється (зафіксовано тестами)
`booking/tests/test_legacy.py` — характеризаційні тести v1, зелені на v1 **до** будь-якого рефакторингу і мають лишатися зеленими без змін у v2:
- `V1OnR100`: форма запису, 201/400/404/409, суміжні інтервали, пошук, скасування (403/200/409), 401 — усе на R100, що в v2 лишається auto-`ACTIVE`.
- `LegacyActiveOnR101`: наявний `ACTIVE` на R101 читається через `mine/` без змін (ID, поля, статус), блокує слот, не змінюється чужими діями й повторним `seed_demo`, власник може його скасувати.
Якщо тест з цього файлу потрібно змінити під v2 — це сигнал про ламання сумісності, а не рутинне оновлення.

## 3. Вплив
| Компонент | Вплив |
|---|---|
| `booking/rooms.py::create` | вибір статусу за `room.capacity`; решта без змін |
| `booking/rooms.py::overlapping` | вже враховує `ACTIVE`+`PENDING` — без змін |
| `booking/models.py` | нові поля аудиту (`decided_by` FK nullable, `decided_at`, `decision`), оголошені nullable; constraint `booking_no_overlap_active` має покривати `status IN (ACTIVE, PENDING)`; нові обмеження додаються до того ж `Meta.constraints` |
| Нові view/URL approvals | новий модуль і маршрути `/api/approvals/...` |
| Клієнти | для R101 тепер отримують `PENDING` замість `ACTIVE`; форма запису та коди помилок не змінюються |

## 4. Дозволи
- Створення, `mine/`, скасування — без змін: власник = `request.user`, чужий запис → 403.
- Approvals: лише `is_staff` (seed: тільки `admin`); інші → 403 `forbidden`, без автентифікації → 401.
- Staff не отримує права скасовувати чужі бронювання і не бачить чужих записів у `mine/`.

## 5. Міграція даних
- Лише адитивні міграції (`0003+`): нові nullable-колонки, без `RunPython`, що змінює статуси.
- Constraint перекриття: drop + create в одній транзакції міграції; наявні `ACTIVE` уже не перетинаються, тож новий constraint (`ACTIVE`/`PENDING`) застосовується без конфліктів (PENDING у v1 не створюються).
- Legacy-записи зберігають ID, кімнату, власника, час і статус. **Без ретроактивного погодження**: наявні `ACTIVE` на R101 не стають `PENDING` і не з'являються в `GET /api/approvals/`; поля аудиту для них `NULL`.
- `seed_demo` лишається ідемпотентним і не чіпає бронювання.

## 6. Варіанти реалізації
| Варіант | Суть | Ризик | Рішення |
|---|---|---|---|
| Локальна зміна | гілка за `capacity` у `create`, новий модуль approvals, адитивна міграція | малий; покрито характеризаційними та контрактними тестами | **Обрано** |
| Поетапна заміна | новий сервіс/шлях створення за прапорцем, паралельна робота v1 і v2, потім перемикання | надлишкова складність для локального демо; дві логіки статусів одночасно | Ні |
| Переписування | новий доменний шар/модель станів | високий ризик регресії legacy і втрати даних, не вкладається в графік | Ні |

## 7. Приймання
1. `booking/tests/test_legacy.py` зелений без змін — і на v1, і на v2.
2. Спільні `qa/test_contract.py` (`test_capacity`, `test_approval`) зелені.
3. `makemigrations --check` чистий; міграція на БД з legacy-даними не змінює їх (порівняння знімка рядків до/після).
4. Конкурентність: паралельні create на R101 → один 201, один 409; паралельні рішення/скасування → лише один перехід (`SELECT ... FOR UPDATE`).
5. Успішно виконати [перевірки з CI](handoff.md#5-тестування).

## 8. Відкат
- Код: revert релізного коміту v2, повторне розгортання v1-образу.
- Схема: міграції v2 мають `reverse` (видалення колонок аудиту, повернення constraint на `status = ACTIVE`). Перед `migrate booking 0002` потрібно вирішити долю нових записів: `PENDING` → `CANCELLED` (v1 їх не обробляє), `REJECTED` лишаються (v1 їх лише показує). Рішення фіксується в інциденті; legacy-записи відкат не зачіпає.
- Перед міграцією вперед — резервна копія БД (`pg_dump`); при невдалому відкаті схеми — відновлення з неї.
- Критерій відкату: будь-який червоний тест з `test_legacy.py` або змінений legacy-рядок після міграції.
