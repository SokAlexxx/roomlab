# B6 — Інцидент: готовність БД і відновлення (KAN-16)

## Дизайн
- `docs/incident.md`: хронологія, гіпотези (web зупинений — відхилено; БД недоступна — підтверджено), спостереження про відновлення, дві коригувальні задачі (власник, віха, верифікація) і залишковий ризик. Усі часи й результати взято лише з наданого `incident.json`.
- `booking/tests/test_recovery.py`: клас `HealthOutageRecovery` (`TransactionTestCase`).

## Метод перевірки
1. `GET /health/` → 200.
2. З'єднання Django закривається, `HOST/PORT` вказують на закритий порт (`127.0.0.1:1`): справжня помилка підключення, не мок. Три запити → 503 з `{"status":503}`.
3. Параметри повертаються, з'єднання закривається → два запити → 200.
Відновлення налаштувань гарантоване через `addCleanup`, навіть якщо тест падає. Спільні тести `qa/` не змінювались.

## Виконання
Виконано `py -3.12 .roomlab-check.py` (Docker-збірка, Ruff, Django check, `makemigrations --check`, migrate, повний набір тестів на PostgreSQL): `ROOMLAB_CHECK_OK`. Новий тест окремо від повного набору не запускався.

## Обмеження
- Імітується втрата з'єднання, а не зупинка контейнера PostgreSQL чи перезапуск БД.
- `/health/` перевіряє лише `SELECT 1`.
- Коригувальні задачі лише заплановані; їхні строки — внутрішні віхи, у `incident.json` їх немає.
