# B5 — Черга і рішення staff v2 (KAN-15)

## Дизайн
- `booking/flow.py`: `GET /api/approvals/` (staff, `PENDING`) і `POST /api/approvals/{id}/decision/`; маршрути в `booking/flow_urls.py`. Скасування `PENDING` власником працює через наявний `cancel` (`CANCELLABLE`).
- Рішення: `transaction.atomic()` + `select_for_update()` на рядку; статус і аудит (`decided_by`, `decided_at`, `decision`) — один `UPDATE`. Перевірка стану лише після блокування, тому гонка рішення/рішення і рішення/скасування серіалізована.
- Те саме рішення повторно → 200 з початковими актором і часом; протилежне, рішення для `CANCELLED` чи legacy `ACTIVE` без аудиту → 409 `invalid_transition`. `reject` і `cancel` звільняють слот.
- Таблиця переходів українською: `docs/decisions.md`.

## Метод перевірки
- `booking/tests/test_decisions.py`: `TestCase` для прав (401/403/405/400/404), аудиту, стабільного повтору (в т.ч. іншим staff), 409 для протилежного, звільнення слоту, скасування `PENDING`.
- `TransactionTestCase` з потоками і окремими з'єднаннями PostgreSQL (перевіряється різний `pg_backend_pid`), бар'єр одночасного старту: протилежні рішення (5 повторів) → рівно `[200, 409]`, аудит збігається з переможцем, слот звільнено/зайнятий відповідно; однакові рішення → однаковий аудит; скасування проти рішення → одна з допустимих узгоджених кінцевих пар.
- Виконано `py -3.12 .roomlab-check.py` (Docker, Ruff, Django check, `makemigrations --check`, migrate, повний набір на PostgreSQL) → `ROOMLAB_CHECK_OK`.

## Обмеження
- Скрипт друкує лише підсумок, тож окремі результати тестів і кількість прогонів я не бачив.
- Гонки недетерміновані: тест перевіряє інваріанти, а не конкретне чергування; порядок блокувань не форсується (немає інструментованих пауз).
- `decided_by` повертається як id користувача. Cancel після схвалення залишає аудит `approve` у скасованому записі.
- Немає пагінації черги.
