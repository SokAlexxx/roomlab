# B4 — Характеризаційні тести v1 і план зміни v2 (KAN-14)

## Дизайн
- `booking/tests/test_legacy.py` фіксує поточну поведінку v1 так, щоб тести лишались валідними у v2 без змін:
  - `V1OnR100` — усі створення через API лише на R100 (capacity 100, у v2 лишається auto-`ACTIVE`): точна форма запису, 201/400/404/409, суміжні `[start,end)`, пошук, скасування 403/200/409, 401.
  - `LegacyActiveOnR101` — legacy `ACTIVE` на R101 вставляється через ORM (як рядок, що існував до міграції v2) і перевіряється: `mine/` повертає його без змін (ID, поля, статус), рядок у БД ідентичний до/після, слот зайнятий, чужі 403 (bob, admin) не змінюють рядок, повторний `seed_demo` не чіпає запис і ID кімнати, власник може скасувати.
  - Нічого, що v2 свідомо змінює (нові бронювання R101, approvals), не перевіряється.
- `docs/change.md`: зміна v2, вплив, дозволи, міграція (адитивна, без ретроактивного погодження), локальна зміна vs поетапна заміна vs переписування (обрано локальну), приймання, відкат.

## Метод перевірки
- Тести — через Django test client на реальних ендпоінтах і PostgreSQL, без моків (крім `DEMO_PASS` у середовищі для `seed_demo`).
- Зелене до рефакторингу: виконано `py -3.12 .roomlab-check.py` (Docker-збірка, Ruff, Django check, `makemigrations --check`, migrate, повний набір тестів на PostgreSQL) на незміненому коді v1 → `ROOMLAB_CHECK_OK`.

## Обмеження
- Legacy-рядок створюється в тестовій БД через ORM, а не міграцією реальних даних; перевірку знімка до/після самої міграції v2 описано в `docs/change.md` як критерій приймання, але тут не виконано (міграції v2 ще немає).
- Відсутність legacy-запису в `GET /api/approvals/` не перевіряється — ендпоінт з'явиться у v2.
- Конкурентні сценарії тут не повторюються; їх покривають `test_create.py` і `qa/test_contract.py`.
