# B2 / KAN-12 — мої бронювання та скасування (v1)

## Дизайн
- `GET /api/bookings/mine/` (`booking/flow.py`, `booking/flow_urls.py`): лише записи `request.user` (встановлює `booking.http.endpoint`), включно з `CANCELLED`/`REJECTED`/`PENDING`; масив `{id,room_id,start,end,status}` за `start`, `id`. Staff не отримує чужих записів.
- `POST /api/bookings/{id}/cancel/`: у `transaction.atomic()` рядок береться через `select_for_update()`, далі по черзі:
  - немає запису → `404 not_found`;
  - чужий власник (зокрема staff) → `403 forbidden`, без змін; власність перевіряється раніше за стан, тож чужий статус не розкривається;
  - стан не `ACTIVE`/`PENDING` → `409 invalid_transition`;
  - інакше `CANCELLED`, `200` з записом. Слот звільняється одразу, бо пошук блокують лише `ACTIVE`/`PENDING`.
- Блокування рядка серіалізує паралельні скасування: друге бачить зафіксований `CANCELLED` і отримує 409.

## Метод тестування
- `booking/tests/test_flow.py` (Django `TestCase`, PostgreSQL). Фікстури створюються напряму через ORM і не залежать від FR-02.
- Що перевіряється:
  - 401 і 405 для обох маршрутів;
  - формат відповіді;
  - ізоляція власників у `mine` (alice/bob/admin), неактивні записи та порядок;
  - скасування власником і звільнення слота (через `/api/rooms/available/`);
  - 403 для bob і admin без жодної зміни рядка (порівняння всіх полів);
  - 403 для чужого неактивного запису; 404 для невідомого id;
  - повторне скасування → 409, а `REJECTED` → 409; скасування `PENDING`;
  - інші записи не змінюються; у SQL є `FOR UPDATE`.
- Спільний `qa/test_contract.py::test_owner` вмикається наявністю цього файлу.

## Обмеження
- Справжню конкурентність двох скасувань окремим `TransactionTestCase` з потоками не перевірено. Перевіряється лише наявність `FOR UPDATE`.
- Тіло запиту cancel ігнорується (за контрактом `{}`). Пагінації в `mine` немає.
- Аудиту (хто/коли скасував) у v1 немає.
