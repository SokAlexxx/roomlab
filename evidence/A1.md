# A1 / KAN-4 — пошук вільних кімнат

## Дизайн
- `GET /api/rooms/available/?start=...&end=...` (`booking/rooms.py`, `booking/rooms_urls.py`), через `booking.http.endpoint("GET")`: 401 без Basic, 405 для інших методів.
- Валідація: `parse_instant` приймає лише ISO 8601 з явним зсувом (`Z` або `±HH:MM`); naive, лише дата, сміття, пробіли, відсутні значення та `start >= end` → `400 invalid_input` через `booking.http.error`.
- Інтервали `[start, end)`: перетин ⇔ `existing.start < end AND existing.end > start`; суміжні бронювання не конфліктують. Блокують `ACTIVE` і `PENDING`; `CANCELLED`/`REJECTED` — ні.
- Один SQL-запит (`NOT IN` підзапит), відповідь — масив `{id,name,capacity}` за `id`.
- `docs/architecture.md`: контекст, компоненти, послідовність створення бронювання, ADR-1 (лише перевірка в застосунку vs exclusion constraint у PostgreSQL; обрано constraint як гарантію).

## Метод тестування
- `booking/tests/test_search.py` (Django `TestCase`, PostgreSQL, перевіряється `connection.vendor`): та сама кімната vs інша кімната, часткові перетини (початок, кінець, всередині, охоплення, 1 с), суміжність з обох боків, інший зсув для того самого моменту, `CANCELLED`/`REJECTED` не блокують, `PENDING` блокує, некоректні часи (13 випадків), 401/405, формат і порядок відповіді, юніт-тести `parse_instant`.
- Спільний `qa/test_contract.py::test_search` вмикається наявністю цього файлу.
- Запуск: `py -3.12 .roomlab-check.py` (Docker, Ruff, `check`, міграції, повний набір тестів на PostgreSQL). Результат див. нижче.

## Обмеження
- Результат пошуку — знімок; кімната може бути зайнята до створення бронювання. Гарантія від гонок — exclusion constraint етапу A2 (ще не реалізований у цьому етапі).
- У query string `+` треба кодувати як `%2B`, інакше значення відхиляється (не вгадується).
- Немає пагінації, фільтра за місткістю чи обмеження довжини інтервалу.
